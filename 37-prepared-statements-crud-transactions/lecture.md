# 37. Prepared statements, CRUD і транзакції

> Що ти вже вмієш: параметризовані запити й транзакції з іншої мови —
> ідеї універсальні · Що додає ця тема: PDO-специфічний API для них,
> плюс N+1 — пастка, в яку рано чи пізно потрапляє кожен · ~30 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `prepare()`/`execute()` — той самий підхід, що й параметризовані
  запити в JDBC (`PreparedStatement`) чи psycopg2 (`cursor.execute(sql,
  params)`): SQL і дані передаються **окремо**, СУБД сама безпечно
  підставляє значення — не рядкова конкатенація.
- Транзакції (`beginTransaction`/`commit`/`rollBack`) — концептуально
  ідентичні будь-якій мові: група операцій виконується атомарно, або
  всі, або жодна.
- N+1 — не PHP-специфічна проблема (той самий біль з Hibernate, Django
  ORM, Sequelize), але тут розглядається на голому SQL/PDO, без ORM, що
  міг би її замаскувати "магією" лінивого завантаження.

## 2. Ключові терміни

- **Placeholder (плейсхолдер)** — `?` (позиційний) чи `:name`
  (іменований) у SQL-запиті, куди PDO безпечно підставляє значення при
  `execute()`.
- **Transaction (транзакція)** — група операцій, що виконується
  атомарно: `commit()` застосовує всі зміни, `rollBack()` скасовує їх
  усі, якщо щось пішло не так посередині.
- **N+1 (проблема N+1 запиту)** — антипатерн: один запит на список
  сутностей + по одному додатковому запиту на "деталі" кожної (N штук)
  — замість одного `JOIN`-запиту.
- **Pagination (пагінація)** — вибірка результату частинами (сторінками)
  через `LIMIT`/`OFFSET`, а не всієї таблиці одразу.

## 3. Теорія

### 3.1 Позиційні й іменовані плейсхолдери

```php
$stmt = $pdo->prepare('SELECT * FROM products WHERE category_id = ? AND price < ?');
$stmt->execute([2, 100.00]); // позиційні — порядок важливий

$stmt = $pdo->prepare('SELECT * FROM products WHERE category_id = :cat AND price < :maxPrice');
$stmt->execute(['cat' => 2, 'maxPrice' => 100.00]); // іменовані — порядок не важливий, читабельніше при багатьох параметрах
```

### 3.2 Транзакції

```php
$pdo->beginTransaction();
try {
    $stmt = $pdo->prepare('INSERT INTO products (name, category_id, price) VALUES (?, ?, ?)');
    foreach ($items as $item) {
        $stmt->execute([$item['name'], $item['category_id'], $item['price']]);
    }
    $pdo->commit();
} catch (\PDOException $e) {
    $pdo->rollBack();
    throw $e; // не приховуй помилку — дай викликачу знати, що вставка не вдалась
}
```

Без транзакції, якщо третій з п'яти `INSERT` провалиться (наприклад,
через порушення `FOREIGN KEY`), перші два **лишаться** в БД —
напівзроблена операція. З транзакцією — або всі п'ять, або жодного.

### 3.3 N+1: антипатерн і виправлення

```php
// ПОГАНО: 1 запит на продукти + N запитів на категорію кожного
$products = $pdo->query('SELECT * FROM products')->fetchAll();
foreach ($products as $product) {
    $stmt = $pdo->prepare('SELECT name FROM categories WHERE id = ?');
    $stmt->execute([$product['category_id']]);
    $product['category_name'] = $stmt->fetchColumn(); // ще один запит НА КОЖЕН продукт!
}

// ДОБРЕ: 1 запит замість N+1
$products = $pdo->query(
    'SELECT p.*, c.name AS category_name FROM products p JOIN categories c ON p.category_id = c.id'
)->fetchAll();
```

Для 100 продуктів перший варіант робить 101 запит до БД, другий — 1.
Різниця непомітна на маленьких даних локально, критична в продакшені під
навантаженням.

### 3.4 Пагінація: `LIMIT`/`OFFSET`

```php
function fetchProductsPage(\PDO $pdo, int $page, int $perPage): array
{
    $offset = ($page - 1) * $perPage;
    $stmt = $pdo->prepare('SELECT * FROM products ORDER BY id LIMIT ? OFFSET ?');
    $stmt->bindValue(1, $perPage, \PDO::PARAM_INT);
    $stmt->bindValue(2, $offset, \PDO::PARAM_INT);
    $stmt->execute();

    return $stmt->fetchAll();
}
```

`LIMIT`/`OFFSET` вимагають **цілих чисел**, не рядків — `execute([$perPage,
$offset])` іноді підставляє їх як рядки (залежно від налаштувань
емуляції), що MySQL може відхилити; `bindValue()` з явним
`PDO::PARAM_INT` — надійніший спосіб для цього конкретного випадку.

## 4. Підводні камені

- `AUTO_INCREMENT` у MySQL **не відкочується** разом з транзакцією:
  якщо `INSERT` встиг згенерувати `id = 5`, а потім транзакцію
  скасовано через `rollBack()`, наступний успішний `INSERT` отримає
  `id = 6`, не `5` — лічильник не "повертається назад". Це очікувана
  поведінка MySQL, не баг: "дірки" в послідовності `id` після
  відкочених транзакцій — нормальні, на них не варто покладатись.
- Забутий `rollBack()` у `catch`-блоці навколо транзакції — з'єднання
  лишається "у транзакції" невизначено, наступні запити поводяться
  непередбачувано. Патерн `try { ... commit() } catch { rollBack();
  throw }` (розділ 3.2) — типовий і майже завжди правильний.
- N+1 непомітний на dev-машині з 5 тестовими рядками й **дуже**
  помітний у продакшені з тисячами — профілювання (яке буде в темах
  професійних практик) чи просто пильна увага до циклів з запитами
  всередині — єдиний надійний захист.
- `OFFSET` для великих сторінок (`OFFSET 100000`) змушує MySQL
  **пройти** й відкинути всі попередні рядки — повільно на великих
  таблицях; для глибокої пагінації існують інші техніки (keyset
  pagination), поза межами цієї теми.

## 5. Сучасний PHP 8.3+

API `prepare()`/`bindValue()`/транзакцій стабільний роками. Що
важливо знати про сучасний PDO загалом — з PHP 8.1 `PDO::ATTR_STRINGIFY_FETCHES`
типово вимкнений (цілі числа повертаються як `int`, не рядком), що вже
видно в поведінці `id`-колонок у попередніх темах цього блоку.

## 6. Контекст екосистеми

ORM (Eloquent, Doctrine) вирішують N+1 через "eager loading"
(`Product::with('category')->get()` у Laravel) — той самий принцип
"один запит замість N+1" (розділ 3.3), просто виражений декларативно.
Розуміння проблеми на голому SQL — те, що дає змогу впізнати N+1 навіть
коли ORM його вдало ховає за зручним синтаксисом.
