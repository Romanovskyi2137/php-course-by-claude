# 48. Деплой та продуктивність

> Що ти вже вмієш: Docker/health-check/reverse proxy — інфраструктурні
> концепції, не PHP-специфічні · Що додає ця тема: PHP-специфічна
> частина — `php-fpm`-пули, OPcache/JIT, і що саме перевіряти в
> health-check ендпоінті · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `php-fpm` (тема 28) — приблизно те, що для Node дає PM2 (кластерний
  режим, кілька воркер-процесів), тільки вбудоване й стандартне для
  PHP, не окремий пакет.
- OPcache — той самий принцип, що JIT-компіляція байткоду в JVM (Java)
  чи V8 (JS/Node): PHP-код компілюється в проміжне представлення один
  раз і кешується, замість перепарсювання файлу на кожен запит.
- Docker-контейнеризація PHP-застосунку — не відрізняється
  концептуально від контейнеризації Node/Python-застосунку: той самий
  `Dockerfile`, той самий принцип "однаково працює локально й у
  продакшені".

## 2. Ключові терміни

- **`php-fpm` пул** — група PHP-воркер-процесів, що обробляють запити;
  розмір пулу (`pm.max_children`) визначає, скільки запитів
  обробляється **одночасно**.
- **OPcache** — вбудоване розширення PHP, що кешує скомпільований
  байткод скриптів у спільній пам'яті — уникає повторного парсингу й
  компіляції PHP-файлу на кожен запит.
- **JIT (Just-In-Time компіляція)** — з PHP 8.0: компіляція "гарячих"
  ділянок байткоду в машинний код під час виконання; дає найбільший
  виграш для CPU-інтенсивних задач (математика, обробка зображень), а
  не для типового I/O-залежного веб-запиту (БД, HTTP-виклики).
- **Health check (перевірка стану)** — ендпоінт (типово `/health`),
  який load balancer/оркестратор (Kubernetes, ECS) періодично опитує,
  щоб знати, чи готовий інстанс приймати трафік.

## 3. Теорія

### 3.1 `php-fpm`: розмір пулу

```ini
; php-fpm pool config
pm = dynamic
pm.max_children = 20      ; максимум одночасних воркерів
pm.start_servers = 5      ; скільки запускається одразу
pm.min_spare_servers = 5  ; мінімум "простоюючих" воркерів напоготові
pm.max_spare_servers = 10
```

Кожен воркер обробляє **один** запит за раз (на відміну від Node,
де один процес обробляє багато запитів асинхронно) — паралелізм у PHP
досягається кількістю **процесів**, не асинхронністю всередині одного.

### 3.2 OPcache: кешування байткоду

```ini
; php.ini
opcache.enable=1
opcache.memory_consumption=128    ; МБ пам'яті під кеш байткоду
opcache.max_accelerated_files=10000
opcache.validate_timestamps=0     ; продакшн: вимкнути перевірку змін файлів
```

`validate_timestamps=0` у продакшені означає: OPcache **не** перевіряє,
чи змінився файл на диску — деплой нового коду вимагає перезапуску
`php-fpm` (чи виклику `opcache_reset()`), інакше старий закешований
байткод виконуватиметься й далі.

### 3.3 JIT: коли він реально допомагає

```ini
opcache.jit=tracing
opcache.jit_buffer_size=64M
```

JIT прискорює **обчислювально важкий** код (математика, парсинг великих
структур) — типовий веб-запит (звернутись до БД, зібрати HTML,
повернути JSON) проводить більшість часу очікуючи I/O (БД, диск,
мережу), де JIT майже нічого не дає. Вмикати JIT варто після
профілювання, коли реально видно CPU-bound ділянку, не "про всяк
випадок".

### 3.4 Health check: що саме перевіряти

```php
function health_check(array $checks): array
{
    $results = [];
    foreach ($checks as $name => $check) {
        $results[$name] = $check() ? 'ok' : 'fail';
    }

    $allOk = !in_array('fail', $results, true);

    return ['status' => $allOk ? 'ok' : 'degraded', 'checks' => $results];
}

health_check([
    'database' => fn () => $pdo->query('SELECT 1') !== false,
    'disk_space' => fn () => disk_free_space('/') > 100 * 1024 * 1024,
]);
// ['status' => 'ok', 'checks' => ['database' => 'ok', 'disk_space' => 'ok']]
```

Хороший health check перевіряє **реальні залежності** застосунку (БД,
диск, зовнішній API) — не просто "чи відповідає PHP взагалі" (це й так
очевидно, якщо ендпоінт узагалі відповів).

## 4. Підводні камені

- `opcache.validate_timestamps=1` (типово для розробки) у продакшені —
  зайві `stat()`-виклики на кожен запит для перевірки, чи змінився
  файл; для продакшену краще `0` + явний `opcache_reset()`/рестарт
  `php-fpm` при деплої.
- Health check, що сам звертається до важких зовнішніх ресурсів на
  **кожен** виклик (наприклад, робить повний тестовий запит до
  стороннього API) — робить сам health check повільним і крихким;
  краще кешувати результат на кілька секунд або перевіряти легші
  сигнали (з'єднання відкрите, а не повний round-trip).
- Мала кількість `pm.max_children` при високому навантаженні — запити
  чекають у черзі на вільний воркер (видно як зростання часу відповіді
  без явної помилки) — типова причина "сайт повільний під
  навантаженням", яку легко пропустити, дивлячись лише на код
  застосунку, а не на конфігурацію `php-fpm`.

## 5. Сучасний PHP 8.3+

JIT — стабільна частина PHP з 8.0, у 8.3 без кардинальних змін. Що
дійсно активно розвивається в екосистемі (контекст, не ядро PHP) —
альтернативні runtime (Swoole, RoadRunner, FrankenPHP, згадані в темі
28) якраз атакують саме той момент, де класична модель "процес на
запит" програє в продуктивності — тримають застосунок у пам'яті між
запитами, уникаючи повторної ініціалізації.

## 6. Контекст екосистеми

Типовий продакшн-стек PHP-застосунку: Docker-контейнер з `php-fpm` +
окремий контейнер nginx (чи один контейнер з обома, залежно від
підходу) + health-check ендпоінт, який опитує оркестратор (Kubernetes,
ECS, чи навіть простий Docker Swarm) перед тим, як направити трафік на
новий інстанс під час деплою.

## 8. Питання для самоперевірки

1. Чим паралелізм у `php-fpm` (кілька процесів) відрізняється від
   асинхронної однопроцесної моделі Node.js?
2. Чому `opcache.validate_timestamps=0` у продакшені вимагає явного
   перезапуску `php-fpm` при деплої нового коду?
3. Для якого типу коду JIT реально дає приріст продуктивності, а для
   якого — майже ні?
4. Що робить health check "хорошим" — які саме залежності варто
   перевіряти, а які перевірки зробили б його повільним чи крихким?
