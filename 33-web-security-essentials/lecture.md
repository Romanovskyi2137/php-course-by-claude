# 33. Основи веб-безпеки

> Що ти вже вмієш: концепції XSS/CSRF/SQLi з іншої мови чи курсу
> безпеки — вони не PHP-специфічні · Що додає ця тема: конкретні
> PHP-інструменти проти кожної з них · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- XSS/CSRF/SQL-ін'єкція — універсальні вебвразливості, не залежать
  від мови бекенду; те, що відрізняється — конкретні інструменти
  захисту. React/Vue екранують вивід автоматично за замовчуванням; у
  голому PHP, що рендерить HTML напряму (тема 28), екранування —
  **твоя** явна відповідальність (`htmlspecialchars()`, розділ 3.1).
- CSRF-токени — той самий підхід, що й `csurf` в Express чи вбудований
  CSRF-захист Django: секретний токен у формі, порівняний із тим, що в
  сесії, перед виконанням дії.
- SQL-ін'єкція — тут лише **прев'ю** (повне рішення — prepared
  statements, тема 37); той самий принцип, що й параметризовані запити
  в будь-якій мові (`?`-плейсхолдери в JDBC, `%s` у psycopg2 з
  параметрами, а не форматуванням рядка).

## 2. Ключові терміни

- **XSS (Cross-Site Scripting)** — впровадження чужого JS-коду на
  сторінку через невиведений безпечно користувацький ввід.
- **CSRF (Cross-Site Request Forgery)** — примушення браузера жертви
  виконати дію (запит) на сайті, де вона вже автентифікована, без її
  відома (наприклад, через автозавантажену форму на чужому сайті).
- **SQL injection (SQL-ін'єкція)** — впровадження SQL-коду через
  неекранований/непараметризований користувацький ввід у запит до БД.
- **Mass assignment (масове присвоєння)** — вразливість, коли весь
  вхідний масив (`$_POST`) напряму йде в конструктор/сеттери сутності
  без білого списку дозволених полів — дозволяючи підмінити поля,
  які користувач не мав права змінювати (наприклад, `is_admin`).
- **CSP (Content Security Policy)** — HTTP-заголовок, що каже браузеру,
  з яких джерел дозволено завантажувати скрипти/стилі/зображення —
  додатковий рубіж захисту від XSS навіть якщо якийсь ввід прослизнув
  неекранованим.

## 3. Теорія

### 3.1 XSS: `htmlspecialchars()`

```php
$comment = '<script>alert("hacked")</script>';

echo $comment; // виведеться й ВИКОНАЄТЬСЯ як HTML/JS у браузері — XSS

echo htmlspecialchars($comment, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
// '&lt;script&gt;alert(&quot;hacked&quot;)&lt;/script&gt;' — виведеться як текст, не виконається
```

Правило без винятків: **будь-який** користувацький ввід, що потрапляє в
HTML-вивід, проходить через `htmlspecialchars()` — незалежно від того,
"здається" він безпечним чи ні (ім'я користувача, коментар, навіть
значення з `<select>`).

### 3.2 CSRF: токен, повʼязаний із сесією

```php
// при рендері форми:
$_SESSION['csrf_token'] ??= bin2hex(random_bytes(32));
// <input type="hidden" name="csrf_token" value="<?= $_SESSION['csrf_token'] ?>">

// при обробці POST:
function verify_csrf_token(?string $expected, ?string $actual): bool
{
    if ($expected === null || $actual === null) {
        return false;
    }

    return hash_equals($expected, $actual);
}

if (!verify_csrf_token($_SESSION['csrf_token'] ?? null, $_POST['csrf_token'] ?? null)) {
    http_response_code(403);
    exit('Некоректний CSRF-токен');
}
```

Чужий сайт може примусити браузер жертви відправити POST-запит (форма,
автоматичний `submit()`), і браузер **автоматично** докладе кукі сесії
жертви — але чужий сайт **не знає** значення `csrf_token` із сесії
жертви, тож підробити його не може.

### 3.3 SQL-ін'єкція: прев'ю (детально — тема 37)

```php
// НІКОЛИ так:
$sql = "SELECT * FROM users WHERE email = '{$email}'";
// $email = "' OR '1'='1" перетворює запит на SELECT * FROM users WHERE email = '' OR '1'='1'
// — повертає ВСІХ користувачів

// Правильно (prepared statement, деталі — тема 37):
$stmt = $pdo->prepare('SELECT * FROM users WHERE email = ?');
$stmt->execute([$email]);
```

### 3.4 Mass assignment: білий список полів

```php
function filter_allowed_fields(array $input, array $allowedFields): array
{
    return array_intersect_key($input, array_flip($allowedFields));
}

// $_POST міг містити 'is_admin' => '1', підкладене вручну через DevTools —
// але воно просто відсутнє в $allowedFields і відфільтровується:
$safeData = filter_allowed_fields($_POST, ['name', 'email', 'bio']);
```

### 3.5 CSP-заголовок

```php
function content_security_policy_header(array $directives): string
{
    $parts = [];
    foreach ($directives as $name => $value) {
        $parts[] = "{$name} {$value}";
    }

    return implode('; ', $parts);
}

header('Content-Security-Policy: ' . content_security_policy_header([
    'default-src' => "'self'",
    'script-src' => "'self'",
]));
// навіть якщо XSS якось прослизнув — браузер відмовиться виконати
// інлайн-скрипт чи скрипт з чужого домену
```

## 4. Підводні камені

- Екранування **лише в одному місці** (наприклад, при збереженні в БД)
  замість **при виводі** — типова помилка: дані можуть виводитись у
  кількох контекстах (HTML, атрибут, JS-рядок), кожен вимагає свого
  екранування саме в момент виводу, а зберігати варто "сирі" дані.
- CSRF-захист **не потрібен** для GET-запитів, які не змінюють стан
  (і GET **не повинен** змінювати стан — ідемпотентність) — токен
  перевіряють на POST/PUT/DELETE-подібні дії.
- `filter_allowed_fields()` (розділ 3.4) захищає лише від "зайвих"
  полів у вхідних даних — це **не** заміна валідації самих значень
  дозволених полів (тема 30); обидва потрібні одночасно.

## 5. Сучасний PHP 8.3+

Самі механізми захисту (`htmlspecialchars()`, `hash_equals()`,
prepared statements) стабільні роками. Що важливо знати про сучасний
PHP загалом — мова **не** захищає від цих вразливостей автоматично
(на відміну від React/шаблонізаторів на кшталт Twig з автоекрануванням
за замовчуванням) — голий PHP, що рендерить HTML напряму (як у цьому
курсі до теми 47), вимагає свідомого застосування кожного інструменту.

## 6. Контекст екосистеми

Twig (типовий шаблонізатор для Symfony, і опційно для інших) екранує
вивід **автоматично** за замовчуванням — саме тому вибір "голий PHP чи
шаблонізатор" впливає на модель безпеки, не лише на зручність
синтаксису. Laravel Blade робить те саме через `{{ }}`. Розуміння того,
що саме відбувається "під капотом" (ця тема) — передумова, щоб довіряти
автоматизації фреймворка, а не просто вірити їй наосліп.

   в момент виводу, а не при збереженні в БД?
2. Чому чужий сайт не може підробити правильно реалізований CSRF-токен,
   навіть знаючи, що жертва залогинена?
3. Чому GET-запити типово не захищають CSRF-токеном?
4. Що саме дає `filter_allowed_fields()` проти mass assignment, і чого
   вона **не** захищає (яку перевірку все одно треба робити окремо)?
