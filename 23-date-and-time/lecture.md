# 23. Дата та час

> Що ти вже вмієш: `Date`/`datetime`/`java.time` з іншої мови · Що додає
> ця тема: чому PHP має **два** класи дати (`DateTime` і
> `DateTimeImmutable`) і чому майже завжди варто брати другий · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `\DateTimeImmutable` — прямий аналог `java.time.LocalDateTime`/
  `Instant` (незмінних, PHP 8.3+) чи Python `datetime` (яка теж завжди
  незмінна). Якщо звик, що дата — value object, який не можна змінити
  "на місці" — це саме воно.
- `\DateTime` (без Immutable) більше схожий на "старий" JS `Date`:
  мутабельний, методи типу `->modify()` змінюють сам об'єкт і повертають
  `$this`. Історично він з'явився в PHP першим; `DateTimeImmutable`
  додали в PHP 5.5 як безпечнішу альтернативу.
- `\DateInterval` — аналог `java.time.Period`/`Duration` чи Python
  `timedelta`: проміжок часу, а не конкретна точка в часі.

## 2. Ключові терміни

- **`DateTimeImmutable`** — незмінний об'єкт дати/часу; будь-яка "зміна"
  (`->add()`, `->modify()`, `->setTimezone()`) повертає **новий** об'єкт,
  оригінал не чіпає.
- **`DateInterval`** — проміжок часу в форматі ISO 8601-подібного рядка
  (`P1D` = 1 день, `P1Y6M` = 1 рік 6 місяців, `PT30M` = 30 хвилин).
- **`DateTimeZone`** — часовий пояс (`'Europe/Kyiv'`, `'UTC'`,
  `'America/New_York'`); визначає, як конкретний момент часу
  відображається в локальному часі й враховує DST (перехід на літній час).
- **Unix timestamp** — кількість секунд з 1 січня 1970 UTC; завжди
  однозначний момент часу, без прив'язки до часового поясу.

## 3. Теорія

### 3.1 Створення й незмінність

```php
$date = new \DateTimeImmutable('2026-08-20');
$tomorrow = $date->add(new \DateInterval('P1D'));

$date === $tomorrow; // false — це два різні об'єкти
$date->format('Y-m-d');     // '2026-08-20' — оригінал не змінився
$tomorrow->format('Y-m-d'); // '2026-08-21'
```

`\DateTime` (мутабельний варіант) робив би `->add()` "на місці" й повертав
би `$this` — а це джерело важких багів, коли той самий об'єкт передається
далі й хтось випадково його змінює. Тому в прикладному коді за замовчуванням
бери `DateTimeImmutable`, а `DateTime` — тільки якщо конкретна бібліотека
цього вимагає.

### 3.2 Парсинг і форматування

```php
$date = new \DateTimeImmutable('2026-08-20 14:30:00');
$date->format('Y-m-d');       // '2026-08-20'
$date->format('d.m.Y H:i');   // '20.08.2026 14:30'

// Суворий парсинг за форматом (щоб '2026-13-40' не "проковтнулось" мовчки):
$strict = \DateTimeImmutable::createFromFormat('!Y-m-d', '2026-08-20');
// '!' на початку формату — скидає час до 00:00:00, а не бере поточний
```

Конструктор `new \DateTimeImmutable($string)` **толерантний**: приймає
купу форматів (`'2026-08-20'`, `'20 August 2026'`, `'next monday'`,
`'+1 week'`) і намагається вгадати. Для довірених внутрішніх даних це
зручно; для введених користувачем рядків, де формат має бути суворо
конкретним, — `createFromFormat()` надійніший (розділ 4).

### 3.3 Арифметика: `add`/`sub`/`diff`

```php
$start = new \DateTimeImmutable('2026-08-20');

$start->add(new \DateInterval('P1D'));   // +1 день
$start->sub(new \DateInterval('P1M'));   // -1 місяць
$start->modify('+3 days');                // те саме простіше, рядком

$end = new \DateTimeImmutable('2026-09-15');
$diff = $start->diff($end); // \DateInterval
$diff->days; // 26 — повна різниця в днях (завжди невід'ємна)
$diff->m;    // 0 — компонент "місяців" у розбитті рік/місяць/день
```

### 3.4 Часові пояси

```php
$utc = new \DateTimeImmutable('2026-01-15 12:00:00', new \DateTimeZone('UTC'));
$kyiv = $utc->setTimezone(new \DateTimeZone('Europe/Kyiv'));

$kyiv->format('Y-m-d H:i:s T'); // '2026-01-15 14:00:00 EET' — той самий момент,
                                  // інше локальне представлення
```

`setTimezone()` **не змінює момент часу** — той самий Unix timestamp
всередині, лише інше "вікно", крізь яке ти на нього дивишся.

## 4. Підводні камені

- `new \DateTimeImmutable('2026-13-45')` **не кидає виняток** — PHP
  "нормалізує" неіснуючу дату (місяць 13 → січень наступного року, тощо)
  або в деяких випадках повертає непередбачуваний результат. Для введених
  користувачем дат завжди перевіряй `createFromFormat()` **плюс**
  порівняння відформатованого результату з вхідним рядком (підказка 1
  у task.md) — інакше "2026-02-30" мовчки перетвориться на якусь іншу дату.
- `$diff->m` і `$diff->days` — це **різні** речі: `->days` — загальна
  кількість повних днів між датами, `->m` — компонент "місяців" у
  розбитті `y`/`m`/`d` (тобто `1 рік 2 місяці` дає `y=1, m=2`, а не
  `m=14`).
- Порівняння дат оператором `<`/`>`/`==` **працює** для `DateTimeImmutable`
  (порівнює момент часу) — не потрібно окремо витягувати timestamp через
  `->getTimestamp()`, хоча інколи це зручно для явності.

## 5. Сучасний PHP 8.3+

PHP 8.3 додав `DateTime::createFromInterface()` і
`DateTimeImmutable::createFromInterface()` — явну конвертацію між
мутабельним і незмінним варіантом в обидва боки (до того працював лише
`createFromMutable()` в один бік). Загальний підхід не змінився: як і
раніше, `DateTimeImmutable` — типовий вибір для нового коду.

## 6. Контекст екосистеми

Робота з часовими поясами й DST-переходами — одне з класичних джерел
багів у будь-якій мові. Практичне правило індустрії: зберігай і рахуй
у **UTC** всередині системи (в БД, у бізнес-логіці), конвертуй у
локальний час користувача лише **на виводі** (розділ 3.4) — так вся
арифметика лишається однозначною.
