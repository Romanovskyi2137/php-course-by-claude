# 24. Регулярні вирази

> Що ти вже вмієш: PCRE-подібний синтаксис з JS/Python/Java · Що додає
> ця тема: PHP-специфічний API (`preg_*`), обов'язкові роздільники й
> модифікатор `u` для UTF-8/кирилиці · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- Синтаксис самих патернів (класи символів, квантифікатори, групи,
  lookahead) — практично ідентичний `re` в Python і regex-літералам у
  JS: PHP використовує бібліотеку **PCRE** (Perl Compatible Regular
  Expressions), яка й надихнула більшість інших мов.
- Головна різниця — API. В JS регулярний вираз — окремий тип
  (`/pattern/flags`), у Python — рядок, який компілюється через
  `re.compile()`. У PHP патерн теж **рядок**, але з обов'язковими
  **роздільниками** навколо (розділ 3.1) — це не опція, а вимога синтаксису.
- `preg_match()` повертає `0`/`1`/`false`, а не сам об'єкт збігу чи
  `null`, як у JS (`String.match()`) чи Python (`re.match()`). Значення
  збігу передається через параметр за посиланням (розділ 3.2) — це
  найчастіша несподіванка для новачків у PHP-regex.

## 2. Ключові терміни

- **PCRE-роздільники (delimiters)** — символи навколо патерну
  (найчастіше `/.../ `), які кажуть PHP, де починається й закінчується
  сам regex, а де — модифікатори.
- **Модифікатор `u`** — вмикає UTF-8-режим: без нього PCRE рахує байти,
  не символи, і кирилиця/будь-які багатобайтові символи ламають
  збіги (розділ 4).
- **Named capture group (іменована група захоплення)** —
  `(?<name>...)` — дає збігу ім'я замість числового індексу, зручно
  діставати за ключем із результату.
- **Greedy vs lazy (жадібний і лінивий квантифікатор)** — `.*` бере
  максимально можливий збіг, `.*?` — мінімально можливий.

## 3. Теорія

### 3.1 Роздільники й базовий синтаксис

```php
$pattern = '/^\d{3}-\d{4}$/';   // '/' — роздільник; можна й '#...#', '~...~' тощо
preg_match($pattern, '123-4567'); // 1 (збіг є)
```

Роздільник обирають так, щоб він не конфліктував із символами всередині
патерну — якщо в регексі багато `/` (наприклад, для URL), зручніше взяти
`#...#` чи `~...~`, щоб не екранувати кожен слеш.

### 3.2 `preg_match` і результат за посиланням

```php
$matched = preg_match('/@([\w.\-]+)$/', 'user@example.com', $matches);
// $matched: 1 (int) — знайдено; 0 — не знайдено; false — помилка в самому патерні
// $matches[0] — весь збіг, $matches[1] — перша група
$matches[1]; // 'example.com'
```

### 3.3 Іменовані групи

```php
preg_match(
    '/^\[(?<date>\d{4}-\d{2}-\d{2})\]\s+(?<level>[A-Z]+):/',
    '[2026-08-20] ERROR: щось зламалось',
    $m
);
$m['date'];  // '2026-08-20' — за ім'ям
$m['level']; // 'ERROR'
$m[1];       // '2026-08-20' — і за числовим індексом теж, обидва працюють
```

### 3.4 `preg_replace` і `preg_split`

```php
preg_replace('/\s+/', ' ', "багато   пробілів\n\nі рядків"); // "багато пробілів і рядків"

preg_replace_callback('/\d+/', fn (array $m) => (string) ((int) $m[0] * 2), 'a1 b22'); // 'a2 b44'

preg_split('/[,;]\s*/', 'a, b;c,  d'); // ['a', 'b', 'c', 'd']
```

### 3.5 Модифікатор `u`: обов'язковий для кирилиці

```php
preg_match_all('/\w+/', 'Привіт світ', $m);
$m[0]; // ['Привіт', 'світ'] або пошкоджені байти — залежно від локалі, ненадійно

preg_match_all('/\p{L}+/u', 'Привіт світ', $m); // з 'u' — надійно
$m[0]; // ['Привіт', 'світ']
```

Без `u` PCRE обробляє рядок як послідовність **байтів**, а не Unicode
code points; кирилиця в UTF-8 — це 2 байти на символ, і без `u`
`\w`/`.`/квантифікатори рахують байти, ламаючи багатобайтові символи
посередині.

## 4. Підводні камені

- Забутий модифікатор `u` — найчастіша причина "регекс працює з
  латиницею, але ламається на кирилиці/емодзі" в PHP-коді. Якщо в
  патерні чи вхідних даних можлива не-ASCII мова — `u` обов'язковий.
- `preg_match()` повертає `int|false`, **не** `bool` — `false` означає
  помилку в самому патерні (наприклад, незбалансовані дужки), а не
  "не знайдено" (це `0`). Перевірка `if (preg_match(...) === 1)` точніша,
  ніж просто `if (preg_match(...))`, якщо важливо відрізнити "нема збігу"
  від "патерн зламаний".
- `preg_replace()` з масивом патернів і масивом замін працює позиційно
  (перший патерн → перша заміна); переплутаний порядок — тиха логічна
  помилка без жодного попередження.

## 5. Сучасний PHP 8.3+

Сам regex-рушій (PCRE2) не змінювався кардинально в 8.3. Практична
рекомендація сучасного PHP лишається незмінною: `u`-модифікатор за
замовчуванням, якщо є найменший шанс не-ASCII вводу — так само, як
`mb_*`-функції за замовчуванням для рядків (тема 05).

## 6. Контекст екосистеми

Регулярні вирази — типовий інструмент для валідації простих форматів
(email-подібний патерн, номер телефону, slug) і парсингу
напівструктурованих текстів (логи, CSV-подібні формати). Для складнішого
парсингу (HTML, JSON, повноцінна граматика) — regex зазвичай **не**
правильний інструмент: відомий жарт "тепер у тебе дві проблеми" про
regex-парсинг HTML виник не просто так — використовуй DOM-парсер чи
`json_decode()` замість regex.
