# 38. Composer та PSR-4

> Що ти вже вмієш: npm/pip/Maven з іншої мови · Що додає ця тема:
> Composer — той самий менеджер залежностей для PHP, плюс PSR-4 —
> угода "простір імен = шлях до файлу", яка робить `require` непотрібним
> · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `composer.json` — прямий аналог `package.json` (npm) чи
  `requirements.txt`/`pyproject.toml` (Python): список залежностей,
  версійні обмеження, метадані пакета.
- `composer install` (за `composer.lock`, як `package-lock.json`) vs
  `composer update` (ігнорує lock, бере найновіші сумісні версії) —
  той самий поділ, що й `npm ci` vs `npm update`.
- PSR-4 — angолог того, що в Java дає структура пакетів
  (`com.example.Foo` → `com/example/Foo.java`) чи в Python — структура
  модулів: **простір імен класу однозначно визначає шлях до файлу**, і
  навпаки. У JS/Node прямого аналога немає (там `require`/`import`
  посилаються на шлях явно) — це найбільш незвична частина для тих, хто
  прийшов з Node.

## 2. Ключові терміни

- **Composer** — офіційний менеджер залежностей PHP: встановлює
  пакети з Packagist (реєстр, як npm/PyPI) і генерує автозавантажувач.
- **`composer.json`** — маніфест проєкту: назва, залежності
  (`require`/`require-dev`), правила автозавантаження (`autoload`).
- **PSR-4** — стандарт автозавантаження: простір імен-префікс мапиться
  на директорію (`"App\\": "src/"` означає `App\Foo\Bar` →
  `src/Foo/Bar.php`).
- **Semver (семантичне версіонування)** — формат версій `MAJOR.MINOR.PATCH`
  і сенс кожної частини: MAJOR — зворотньонесумісні зміни, MINOR — нова
  функціональність без поломок, PATCH — виправлення багів.

## 3. Теорія

### 3.1 `composer init` і структура `composer.json`

```bash
composer init   # інтерактивний майстер, генерує composer.json
```

```json
{
    "name": "yourname/topic-38",
    "type": "project",
    "require": {
        "php": ">=8.3"
    },
    "autoload": {
        "psr-4": {
            "App\\": "src/"
        }
    }
}
```

### 3.2 PSR-4: простір імен ↔ шлях до файлу

```
"App\\": "src/"     // мапінг з composer.json

App\Money            → src/Money.php
App\Billing\Invoice  → src/Billing/Invoice.php
```

Клас `Money` у файлі `src/Money.php` повинен оголосити
`namespace App;` — без цього автозавантажувач не знайде клас за
очікуваним іменем.

### 3.3 Автозавантажувач: `vendor/autoload.php`

```bash
composer dump-autoload   # перегенерувати автозавантажувач без встановлення пакетів
```

```php
require __DIR__ . '/vendor/autoload.php';

$money = new \App\Money(1500, 'UAH'); // жодного require 'src/Money.php' — Composer знайшов сам
```

Composer генерує `vendor/autoload.php` на основі PSR-4-мапінгу: при
першому зверненні до `App\Money` автозавантажувач обчислює шлях
(`src/Money.php`) і підключає файл сам — саме тому в сучасному PHP-коді
майже не буває ручних `require`/`include` для власних класів.

### 3.4 `composer require` і semver-обмеження

```bash
composer require monolog/monolog        # найновіша сумісна версія
composer require monolog/monolog:^3.0   # явне обмеження
```

```
^3.0   — сумісні релізи в межах major 3: >=3.0.0, <4.0.0
~3.1   — >=3.1.0, <3.2.0 (менш поширений, вужчий діапазон)
3.1.4  — точна версія, без оновлень
```

`^` — типовий, найзручніший вибір: дозволяє отримувати виправлення
багів і нову функціональність, але захищає від випадкових breaking
changes при `composer update`.

## 4. Підводні камені

- Клас у файлі, чий шлях **не** відповідає PSR-4-мапінгу з
  `composer.json` (наприклад, `App\Money` у `src/money.php` — інший
  регістр, чи в `src/Models/Money.php` без відповідного піднамепростору)
  — автозавантажувач просто не знайде клас, і `class_exists()`
  поверне `false` без зрозумілої причини. Регістр і структура директорій
  мають збігатись з namespace **точно**.
- Зміни в `composer.json` (додав новий namespace-мапінг, перейменував
  клас) **не** підхоплюються автоматично — після зміни `autoload` завжди
  потрібен `composer dump-autoload`.
- Плутанина `require` (як залежність, версійне обмеження) з `require`
  (мовна конструкція PHP, `require 'file.php'`) — різні речі з однаковою
  назвою; Composer-залежності підключаються автоматично через
  автозавантажувач, ручний `require` для них не потрібен і не пишеться.

## 5. Сучасний PHP 8.3+

Composer 2.x (стандарт з 2021) значно швидший за Composer 1.x і має
кращу підтримку паралельних завантажень пакетів — версія не PHP-8.3-
специфічна, але варто переконатись, що встановлена саме Composer 2.

## 6. Контекст екосистеми

**Кожен** сучасний PHP-фреймворк (Laravel, Symfony, Slim) вимагає
Composer — це не опціональний інструмент, а фундамент екосистеми з
2012 року (коли Composer з'явився й уніфікував те, що раніше кожен
проєкт вирішував по-своєму). PSR-4 конкретно — стандарт, узгоджений
PHP-FIG (PHP Framework Interop Group), тим самим органом, що визначає й
інші PSR (PSR-1/12 — тема 39, PSR-3 логування — тема 46).

## 8. Питання для самоперевірки

1. Що саме мапить `"autoload": {"psr-4": {"App\\": "src/"}}` і як це
   впливає на шлях до файлу класу `App\Billing\Invoice`?
2. Чому після зміни `autoload`-секції потрібен `composer dump-autoload`?
3. Що означає `^3.0` як версійне обмеження — які версії воно дозволяє,
   яких не дозволяє?
4. Чим `composer.lock` відрізняється від `composer.json` і чому обидва
   потрібні?
