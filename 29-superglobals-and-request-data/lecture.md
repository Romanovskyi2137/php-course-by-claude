# 29. Суперглобали та дані запиту

> Що ти вже вмієш: `req.query`/`req.body`/`request.GET` з іншої мови ·
> Що додає ця тема: PHP кладе дані запиту у звичайні глобальні масиви —
> зручно, але легко довіритись їм забагато · ~20 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `$_GET`/`$_POST` — прямі аналоги `req.query`/`req.body` (Express) чи
  `request.GET`/`request.POST` (Django). Головна різниця: у PHP це не
  властивості об'єкта запиту, а **справжні глобальні змінні**, доступні
  з будь-якої точки скрипта без явної передачі.
- `$_SERVER` — приблизно те, що в Node дають комбіновано `req.headers` +
  `req.socket` + змінні оточення процесу: метод, URI, заголовки (як
  `HTTP_*`-ключі), IP клієнта, і купа технічних деталей запиту.
- На відміну від Express (`req.body` вимагає `body-parser`/
  `express.json()` мідлвар), у PHP `$_POST` заповнюється **автоматично**
  для `application/x-www-form-urlencoded` і `multipart/form-data` —
  але **не** для JSON-тіла (розділ 3.3), яке доводиться читати вручну.

## 2. Ключові терміни

- **Superglobal (суперглобальна змінна)** — масив, доступний у будь-якому
  скоупі без `global`: `$_GET`, `$_POST`, `$_SERVER`, `$_COOKIE`,
  `$_SESSION`, `$_FILES`, `$_ENV`, `$_REQUEST`.
- **`php://input`** — потік для читання "сирого" тіла запиту — єдиний
  спосіб дістати JSON/XML-тіло, яке PHP не парсить автоматично.
- **`$_SERVER`** — суперглобал з метаданими запиту й оточення: метод,
  URI, заголовки (`HTTP_*`), IP, шляхи скриптів.
- **Trust boundary (межа довіри)** — умовна лінія між "даними від
  клієнта" (усе в `$_GET`/`$_POST`/`$_SERVER`/`$_FILES` — потенційно
  підроблене) і "даними, яким я довіряю" (після валідації).

## 3. Теорія

### 3.1 `$_GET`/`$_POST`/`$_REQUEST`

```php
// URL: /search?q=php&page=2
$_GET['q'];    // 'php'
$_GET['page']; // '2' — рядок, навіть якщо виглядає як число!

// <form method="POST"><input name="email">...
$_POST['email'];

$_REQUEST['q']; // об'єднання $_GET + $_POST (+ $_COOKIE, залежно від ini) —
                  // уникай: незрозуміло, звідки саме прийшло значення
```

Усі значення в `$_GET`/`$_POST` — **рядки** (або масиви рядків для
`name[]`-полів), навіть якщо в URL написано число. Порівняння без
приведення типів (`$_GET['page'] === 2`) завжди `false` — потрібне явне
приведення чи `filter_var()` (тема 30).

### 3.2 `$_SERVER`: метадані запиту

```php
$_SERVER['REQUEST_METHOD'];  // 'GET', 'POST', ...
$_SERVER['REQUEST_URI'];     // '/search?q=php' — шлях + query як є
$_SERVER['HTTP_USER_AGENT']; // значення заголовка User-Agent
$_SERVER['HTTP_X_FORWARDED_FOR']; // якщо є проксі/балансувальник попереду
$_SERVER['REMOTE_ADDR'];     // IP джерела запиту (проксі — теж IP, не клієнта!)
```

Будь-який HTTP-заголовок `X-Foo-Bar` потрапляє в `$_SERVER` як
`HTTP_X_FOO_BAR` (верхній регістр, дефіси → підкреслення).

### 3.3 JSON-тіло: `php://input`

```php
$raw = file_get_contents('php://input');
$data = json_decode($raw, associative: true, flags: JSON_THROW_ON_ERROR);
```

`$_POST` заповнюється лише для `Content-Type:
application/x-www-form-urlencoded` чи `multipart/form-data` — типових
HTML-форм. Для JSON API (тема 45) `$_POST` буде **порожнім**, навіть
якщо клієнт відправив тіло — тіло треба прочитати напряму з
`php://input`.

### 3.4 Довіра до вхідних даних

```php
function client_ip(array $server): string
{
    if (isset($server['HTTP_X_FORWARDED_FOR'])) {
        [$first] = explode(',', $server['HTTP_X_FORWARDED_FOR']);
        return trim($first);
    }
    return $server['REMOTE_ADDR'] ?? 'unknown';
}
```

`X-Forwarded-For` — заголовок, який ставить проксі/балансувальник, але
його так само легко підробити самому клієнту, якщо проксі перед
застосунком немає чи не перезаписує вхідний заголовок. Довіряти йому
можна лише якщо точно відомо, що застосунок стоїть за проксі, який сам
контролює це значення.

## 4. Підводні камені

- Читання `$_GET`/`$_POST`/`$_SERVER` **напряму всередині** бізнес-логіки
  (а не на самому "краю" застосунку) робить код нетестовним — той самий
  антипатерн, що й читання `$argv` напряму в чистих функціях (checkpoint
  1). Правильний підхід: дістати потрібні значення на межі (front
  controller) і передати їх у функції як звичайні параметри.
- `php://input` можна прочитати **лише один раз** за замовчуванням для
  деяких конфігурацій (POST + `enctype=multipart/form-data` після
  парсингу `$_POST`/`$_FILES`) — якщо потрібно і те, і те, читай
  `php://input` **до** звернення до `$_POST` у неоднозначних випадках.
- `$_SERVER['REMOTE_ADDR']` — це IP останнього "хопа" (проксі, якщо він
  є), не обов'язково реальний IP клієнта; `X-Forwarded-For` теж не
  абсолютна істина (розділ 3.4) — для точного визначення IP за проксі
  потрібна довірена конфігурація самого проксі.

## 5. Сучасний PHP 8.3+

Суперглобали — стабільна, майже незмінна частина PHP з ранніх версій.
Що дійсно змінилось з часом (варто знати, не 8.3-специфічно) —
`register_globals` (автоматичне перетворення `$_GET['x']` на глобальну
`$x`) видалили ще в PHP 5.4: сьогодні доступ до даних запиту **завжди**
явний, через суперглобали, без магії.

## 6. Контекст екосистеми

Фреймворки (Laravel `Request`, Symfony `Request`) обгортають суперглобали
в об'єкт із методами (`$request->query('q')`, `$request->input('email')`)
— не тому, що суперглобали "погані", а щоб дані запиту можна було легко
підмінити в тестах (передати фейковий `Request`-об'єкт) замість
маніпуляцій глобальним станом. Функції в цій темі, що приймають масив
замість читання `$_GET` напряму (розділ 4), — той самий принцип у
мініатюрі.

## 8. Питання для самоперевірки

1. Чому значення в `$_GET`/`$_POST` завжди рядки, навіть коли в URL
   написано число?
2. Чому `$_POST` порожній, коли клієнт відправляє JSON-тіло, і як його
   тоді прочитати?
3. Чому небезпечно беззастережно довіряти `X-Forwarded-For`?
4. Чому краще читати суперглобали на "межі" застосунку й передавати
   значення в чисті функції, а не звертатись до `$_GET` всередині
   бізнес-логіки?
