# 30. Форми, валідація та завантаження файлів

> Що ти вже вмієш: `<form>` і валідація з іншої мови/фреймворку · Що
> додає ця тема: вбудований `filter_var()` для валідації без бібліотек,
> PRG-патерн проти повторної відправки форми, і чому НІКОЛИ не можна
> довіряти `$_FILES['type']` · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- `filter_var()` — вбудований валідатор/санітайзер на рівні мови, без
  зовнішньої бібліотеки; функціонально ближче до `zod`/`joi` (JS) чи
  Django Forms, тільки менш декларативний — одне значення за раз,
  не схема цілого об'єкта.
- `$_FILES` — структура даних про завантажені файли, схожа на
  `req.files` в Express (з `multer`) чи `request.FILES` у Django, але
  вбудована в мову без жодного мідлвара — PHP парсить
  `multipart/form-data` сам.
- PRG (`Post/Redirect/Get`) — той самий патерн, що й "redirect after
  submit" у будь-якому веб-фреймворку: не PHP-специфіка, але тут явно
  проговорена, бо новачки в PHP часто пишуть форми без нього й
  дивуються дублюючим замовленням при F5.

## 2. Ключові терміни

- **`filter_var()`** — вбудована функція валідації/санітайзації одного
  значення за визначеним фільтром (`FILTER_VALIDATE_EMAIL`,
  `FILTER_VALIDATE_INT`, `FILTER_SANITIZE_*` тощо).
- **PRG (Post/Redirect/Get)** — патерн: POST-обробник валідує/зберігає
  дані й відповідає `redirect` (не HTML напряму); браузер потім
  робить GET на нову адресу — оновлення сторінки (F5) більше не
  надсилає форму повторно.
- **`$_FILES`** — суперглобал зі структурою завантажених файлів:
  `name`, `type`, `tmp_name`, `error`, `size` для кожного поля форми.
- **MIME sniffing (визначення типу за вмістом)** — визначення
  справжнього типу файлу за його байтами (`finfo`), а не за
  клієнтським полем `type`, яке легко підробити.

## 3. Теорія

### 3.1 `filter_var()`: валідація без ручних regex

```php
filter_var('user@example.com', FILTER_VALIDATE_EMAIL); // 'user@example.com'
filter_var('not-an-email', FILTER_VALIDATE_EMAIL);      // false

filter_var('42', FILTER_VALIDATE_INT);                  // 42 (int!)
filter_var('abc', FILTER_VALIDATE_INT);                 // false

filter_var('25', FILTER_VALIDATE_INT, [
    'options' => ['min_range' => 13, 'max_range' => 120],
]); // 25 — у межах діапазону

filter_var('5', FILTER_VALIDATE_INT, [
    'options' => ['min_range' => 13, 'max_range' => 120],
]); // false — поза діапазоном
```

При невдачі `filter_var()` завжди повертає `false` — важливо перевіряти
саме `=== false`, а не просто falsy (`0` — валідне ціле число, але
falsy).

### 3.2 PRG-патерн

```
Без PRG:                          З PRG:
POST /order  → 200 OK (HTML)      POST /order  → 302 Found (Location: /order/success)
[F5] → повторний POST!            GET /order/success → 200 OK (HTML)
                                   [F5] → просто повторний GET, безпечно
```

Обробник форми (`public/submit.php`) не рендерить HTML напряму — він
обробляє дані й відповідає `header('Location: ...')` + `exit`, куди
браузер автоматично робить GET-запит.

### 3.3 `$_FILES`: структура завантаженого файлу

```php
// <input type="file" name="avatar">
$_FILES['avatar'];
// [
//     'name'     => 'photo.jpg',       // ім'я файлу з боку клієнта
//     'type'     => 'image/jpeg',      // MIME-тип, ЗАЯВЛЕНИЙ клієнтом (не довіряй!)
//     'tmp_name' => '/tmp/php7A2B.tmp', // тимчасовий шлях на сервері
//     'error'    => 0,                  // UPLOAD_ERR_OK, або код помилки
//     'size'     => 204800,             // розмір у байтах
// ]
```

### 3.4 Перевірка реального типу файлу через `finfo`

```php
if ($_FILES['avatar']['error'] !== UPLOAD_ERR_OK) {
    throw new \RuntimeException('Помилка завантаження');
}

$finfo = new \finfo(FILEINFO_MIME_TYPE);
$realType = $finfo->file($_FILES['avatar']['tmp_name']); // читає перші байти файлу

if (!in_array($realType, ['image/jpeg', 'image/png'], strict: true)) {
    throw new \RuntimeException("Недозволений тип файлу: {$realType}");
}
```

`finfo` дивиться на реальні байти файлу (magic bytes), а не на ім'я чи
заявлений `Content-Type` — саме тому це надійна перевірка, на відміну
від `$_FILES['avatar']['type']`.

## 4. Підводні камені

- `$_FILES['avatar']['type']` **встановлює клієнт** (браузер бере його з
  розширення файлу чи заголовка запиту) — зловмисник може перейменувати
  `payload.php` в `photo.jpg` і виставити `type: image/jpeg` вручну через
  будь-який HTTP-клієнт, минаючи браузер. Єдина надійна перевірка —
  `finfo` по реальному вмісту файлу (розділ 3.4).
- `filter_var($value, FILTER_VALIDATE_INT)` повертає `false` при
  невдачі, а `0` — цілком валідний результат для вхідного `"0"`. Перевірка
  `if (!filter_var(...))` **неправильна** (сплутає `0` з невдачею) —
  завжди `=== false`.
- Форма без PRG, що рендерить результат напряму в HTML-відповіді на
  POST, — джерело класичного бага "подвійне замовлення при F5"
  (браузер попереджає про повторну відправку, але користувачі тиснуть
  "Так" не читаючи).

## 5. Сучасний PHP 8.3+

`filter_var()` і `$_FILES` — стабільний, давно усталений API. Що
змінилось у 8.1+ (варто знати, не 8.3-специфічно): `enum`-и (тема 18)
добре пасують для представлення `UPLOAD_ERR_*`-кодів у власному коді
типобезпечно, замість "сирих" `int`-констант — хоча самі вбудовані
константи лишаються звичайними `int`.

## 6. Контекст екосистеми

Фреймворки зазвичай додають декларативну валідацію (Laravel
`$request->validate([...])`, Symfony `Validator`-компонент) поверх тих
самих ідей: правило на поле, збір помилок, ре-рендер форми зі старими
значеннями при провалі. `filter_var()` — те, з чого це "під капотом"
починається в голому PHP.
