# 31. Куки та сесії

> Що ти вже вмієш: `express-session`/Django sessions/JWT з іншої мови ·
> Що додає ця тема: PHP-вбудований механізм сесій "з коробки" — файл на
> диску сервера + одна кука з ID, без окремої бібліотеки · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- HTTP сам по собі — протокол без пам'яті (stateless, тема 28): кожен
  запит незалежний. Куки й сесії — це те, як **будь-яка** мова емулює
  "пам'ять" поверх цього; ідея однакова всюди, PHP просто дає
  вбудовану реалізацію без стороннього пакета (на відміну від
  `express-session`, куди явно підключається сховище).
- Типовий PHP-механізм: `session_start()` ставить клієнту куку з
  випадковим ID сесії, а самі дані (`$_SESSION`) зберігаються на
  **сервері** (типово — файл у `/tmp` чи де налаштовано). Це ближче
  до Django-сесій за замовчуванням, ніж до "все в JWT в куці" —
  дані не покидають сервер, клієнт тримає лише ID.
- `$_SESSION` поводиться як звичайний асоціативний масив — не потрібен
  окремий клієнт "сесійного сховища", як `req.session.set()` деінде.

## 2. Ключові терміни

- **Cookie (кука)** — маленький шматок даних, який сервер просить
  браузер зберігати й автоматично надсилати назад із кожним наступним
  запитом на той самий домен.
- **Session (сесія)** — дані, повʼязані з конкретним відвідувачем, що
  живуть на **сервері**; клієнт тримає лише session ID (типово в куці
  `PHPSESSID`).
- **`HttpOnly`** — прапорець куки: недоступна з JS (`document.cookie`)
  — захист від крадіжки session ID через XSS (тема 33).
- **`SameSite`** — прапорець куки, що обмежує, коли браузер надсилає
  куку при переходах з інших сайтів — основний вбудований захист від
  CSRF (тема 33) на рівні браузера.
- **Session fixation (фіксація сесії)** — атака, коли зловмисник
  примушує жертву використати відомий йому наперед session ID; захист —
  `session_regenerate_id()` після зміни рівня привілеїв (логін).

## 3. Теорія

### 3.1 Куки: `setcookie()`

```php
setcookie('theme', 'dark', [
    'expires' => time() + 86400 * 30, // 30 днів
    'path' => '/',
    'secure' => true,      // лише через HTTPS
    'httponly' => true,    // недоступна з JS
    'samesite' => 'Lax',   // не надсилається при кросдоменних запитах
]);

$_COOKIE['theme']; // 'dark' — доступна лише в НАСТУПНОМУ запиті, не в тому самому
```

`setcookie()` лише **додає заголовок** `Set-Cookie` у відповідь — сама
кука з'явиться в `$_COOKIE` тільки при наступному запиті від браузера,
не одразу в тому самому скрипті, де її встановили.

### 3.2 Сесії: `session_start()`

```php
session_start();               // читає PHPSESSID-куку (чи створює нову) + завантажує $_SESSION
$_SESSION['user_id'] = 42;     // звичайний масив — записується на диск в кінці запиту
$_SESSION['cart'][] = $item;

session_destroy();             // знищує дані сесії на сервері (саму куку варто прибрати окремо)
```

`session_start()` **мусить** викликатись до будь-якого виводу (розділ
3.4 теми 28 — той самий принцип, що й для `header()`, бо сесія теж
ставить куку через заголовок).

### 3.3 Regenerate ID: захист від session fixation

```php
// після успішного логіну:
session_regenerate_id(true); // true — видалити старий файл сесії на сервері
$_SESSION['user_id'] = $user->id;
```

Якщо не регенерувати ID при зміні рівня привілеїв (анонім → залогинений
користувач), зловмисник, який якимось чином дізнався **старий** ID сесії
жертви ще до логіну, зможе користуватись тією самою сесією й після її
логіну.

### 3.4 Таймаут неактивності

```php
$maxIdleSeconds = 1800; // 30 хв
if (isset($_SESSION['last_activity']) && (time() - $_SESSION['last_activity']) > $maxIdleSeconds) {
    session_destroy();
    // редірект на логін
}
$_SESSION['last_activity'] = time();
```

PHP сам не видаляє "неактивні" сесії негайно (лише за
`session.gc_maxlifetime` — коли завгодно, garbage collector не
детермінований) — явний таймаут по `last_activity` у власному коді
надійніший, якщо потрібна передбачувана поведінка.

## 4. Підводні камені

- `header()`/`setcookie()`/`session_start()` **не працюють** у CLI SAPI
  (тема 28, розділ 4) — `headers_sent()` там одразу `true`. Тому логіку
  цієї теми перевіряють через чисті функції, що приймають/повертають
  масив, який імітує `$_SESSION`, а реальний `session_start()` —
  дивись живим у `public/` через `php -S`.
- Кука встановлюється лише в **наступному** запиті (розділ 3.1) — код,
  що встановлює й одразу в тому самому скрипті читає `$_COOKIE`,
  побачить **старе** значення (чи його відсутність).
- Забутий `session_regenerate_id()` після логіну — реальна вразливість
  (session fixation, розділ 3.3), а не теоретична: якщо ID сесії видно
  до логіну (наприклад, у URL за старих часів, чи через XSS), і
  сервер не змінює його при підвищенні привілеїв — захопити сесію
  простіше, ніж вкрасти пароль.

## 5. Сучасний PHP 8.3+

Параметр `setcookie()`/`session_set_cookie_params()` у вигляді масиву
опцій (а не окремих позиційних аргументів `expires, path, domain,
secure, httponly`) — стандарт з PHP 7.3+, і саме так варто писати новий
код: явні ключі (`'samesite' => 'Lax'`) читабельніші й менш крихкі до
помилок у порядку аргументів, ніж довгий позиційний виклик.

## 6. Контекст екосистеми

Альтернатива серверним сесіям — **stateless**-автентифікація через JWT
(тема 46): дані самого токена підписані й перевіряються без звернення
до серверного сховища. У традиційних веб-застосунках (не API) серверні
сесії й досі домінують — простіші в реалізації (не треба думати про
відкликання токена) і природно пасують до моделі "сервер рендерить
HTML".

4. Чому `HttpOnly`-прапорець важливий саме для куки з session ID?
