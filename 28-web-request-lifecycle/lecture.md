# 28. Життєвий цикл веб-запиту

> Що ти вже вмієш: Express/Django/Spring — довгоживучий процес, що слухає
> порт · Що додає ця тема: PHP типово влаштований інакше — окремий,
> "чистий" процес на кожен запит · ~25 хв

## 1. Якщо ти прийшов з JS / Python / Java

- У Node/Express процес запускається **один раз** і живе довго,
  обробляючи запити один за одним у тому самому процесі — глобальний
  стан (змінна в модулі) переживає між запитами, якщо явно не скинутий.
- Класичний PHP (через `php-fpm`) працює інакше: кожен HTTP-запит
  обробляється **з чистого аркуша** — новий виклик скрипта, весь стан
  (змінні, підключення до БД, все, крім зовнішніх сховищ типу сесій/БД)
  зникає в кінці запиту. Це ближче до "serverless"-функції (AWS
  Lambda/Cloud Functions) на кожен запит, ніж до довгоживучого сервера.
- `php artisan serve`-подібні dev-сервери (в PHP — вбудований
  `php -S`, розділ 3.2) чи Node — обидва зручні для розробки, але в
  продакшні PHP типово ховається за nginx + `php-fpm` (розділ 3.1), не
  за власним HTTP-сервером на кшталт `express().listen()`.

## 2. Ключові терміни

- **SAPI (Server API)** — інтерфейс, через який PHP-рушій спілкується з
  сервером; `cli` (термінал), `cli-server` (вбудований dev-сервер),
  `fpm-fcgi` (php-fpm) — різні SAPI, той самий мовний рушій.
- **`php-fpm` (FastCGI Process Manager)** — пул PHP-процесів-воркерів,
  яким nginx/Apache передають запити через протокол FastCGI; типова
  продакшн-конфігурація PHP.
- **Shared-nothing (нічого спільного)** — архітектурна модель, де кожен
  запит ізольований і не ділить стан із сусідніми запитами (окрім
  зовнішніх сховищ — БД, сесій, файлів).
- **Front controller (єдина точка входу)** — патерн, де **весь**
  HTTP-трафік проходить через один файл (`index.php`), який далі
  маршрутизує запит — на відміну від "файл на URL" (`/about.php` →
  `about.php`), типового для дуже старого PHP.

## 3. Теорія

### 3.1 Шлях запиту: nginx → php-fpm → PHP-процес

```
Браузер → nginx (веб-сервер, віддає статику й проксіює динаміку)
        → php-fpm (пул PHP-воркерів, протокол FastCGI)
        → один PHP-процес виконує index.php з нуля до кінця
        → результат (HTML/JSON/...) повертається тим самим шляхом назад
```

nginx сам PHP не виконує — він або віддає статичні файли (CSS/JS/
картинки) напряму, або передає запит `*.php` через FastCGI в `php-fpm`,
який тримає пул уже "прогрітих" PHP-воркерів (не запускає новий процес
на кожен запит "з нуля" — воркер переживає між запитами, але **змінні
всередині скрипта** — ні).

### 3.2 Вбудований сервер: `php -S`

```bash
php -S localhost:8000 -t public/
```

Однопроцесний HTTP-сервер, вбудований у сам PHP — зручний для розробки й
навчання (не треба піднімати nginx), **офіційно не призначений для
продакшену** (немає пулу воркерів, обробляє по одному запиту за раз).
`-t public/` — "document root", директорія, з якої віддаються файли.

### 3.3 Один запит = один прогін скрипта

```php
// public/index.php
$counter = ($counter ?? 0) + 1;
echo $counter; // завжди виведе 1 — щоразу новий запит, змінна не "пам'ятає" минулий раз
```

Немає глобального `$counter`, що росте між запитами, як було б у
довгоживучому Node-процесі — кожен запит отримує чисту пам'ять. Дані, що
повинні пережити один запит (лічильник відвідувань, кошик покупок),
зберігаються **поза** самим PHP-процесом: у сесії (тема 31), у БД (блок
E), у файлі.

### 3.4 `header()` і момент, коли їх уже пізно відправляти

```php
header('Content-Type: application/json');
echo json_encode(['ok' => true]); // тіло відповіді

// А ТАК — уже НЕ спрацює:
echo "щось вивелось раніше";
header('Location: /login'); // Warning: headers already sent
```

HTTP-відповідь має чіткий порядок: спершу заголовки, потім тіло. Щойно
PHP вивів хоч один байт тіла (навіть випадковий пробіл до `<?php` у
файлі!) — заголовки вважаються "відправленими", і подальші виклики
`header()` кидають попередження й нічого не роблять.

## 4. Підводні камені

- Найчастіша причина "Warning: headers already sent" у новачків —
  порожній рядок чи `BOM`-символ **перед** `<?php` у файлі, який
  підключається раніше за виклик `header()`. Виправляється: жодних
  символів до `<?php` в файлах-бібліотеках (тільки в самому front
  controller допустимий HTML після PHP-блоку).
- У CLI (`php script.php` у терміналі) `header()`/сесії/куки **не
  мають реального ефекту** — там немає HTTP-з'єднання, якому їх
  відправляти. Тому код, що працює з `header()`/`$_SESSION`, перевіряють
  реальним запуском через `php -S` і браузер, а не через `check.php`
  (розділ 6 і `public/` цієї теми).
- "Shared-nothing" — це фіча, не баг: вона робить кожен запит
  незалежним і легко масштабованим (просто додай ще воркерів php-fpm),
  але означає, що будь-який стан, важливий між запитами, треба свідомо
  й явно зберігати назовні.

## 5. Сучасний PHP 8.3+

`php-fpm` і модель "процес на запит" — стабільна архітектура, що не
змінювалась кардинально роками. Що справді змінюється в екосистемі
(вартий згадки контекст, не частина ядра PHP) — застосунки на кшталт
Swoole/RoadRunner/FrankenPHP, які запускають PHP-застосунок як
довгоживучий процес (ближче до Node-моделі) заради продуктивності;
стандартний, "з коробки" PHP і досі — shared-nothing per-request.

## 6. Контекст екосистеми

Усі сучасні PHP-фреймворки (Laravel, Symfony, Slim) використовують
front controller — один `public/index.php`, що приймає весь трафік і
маршрутизує запит усередині PHP, а не покладається на файлову структуру
URL. Тема 45 (REST API на голому PHP) побудує саме такий маршрутизатор
власноруч, щоб побачити, що саме роблять фреймворки "під капотом".

## 8. Питання для самоперевірки

1. Чим модель "процес на запит" (php-fpm) відрізняється від
   довгоживучого Node/Express-процесу з точки зору глобального стану?
2. Що станеться, якщо викликати `header()` після того, як скрипт уже щось
   вивів через `echo`?
3. Для чого призначений `php -S` і чому його не використовують у продакшені?
4. Чому `$_SESSION`/`header()` не варто перевіряти автоматичним
   `check.php`, який запускається через CLI?
