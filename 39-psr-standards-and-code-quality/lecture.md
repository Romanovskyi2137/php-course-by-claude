# 39. PSR-стандарти та якість коду

> Що ти вже вмієш: ESLint+Prettier / Black+mypy / Checkstyle з іншої
> мови — та сама ідея, інші назви · Що додає ця тема: конкретні
> PHP-FIG стандарти (PSR-1/12) і інструментарій (PHPStan, php-cs-fixer)
> · ~20 хв

## 1. Якщо ти прийшов з JS / Python / Java

- PSR (PHP Standards Recommendations) — те, чим для JS є домовленості
  навколо ESLint/Prettier, для Python — PEP 8, для Java — Google
  Style Guide. Різниця: PSR — не де-факто конвенція одного інструменту,
  а формальні документи від PHP-FIG (консорціуму авторів найбільших
  PHP-фреймворків), яких дотримується практично весь екосистемний код.
- PHPStan/Psalm — аналоги `mypy` (Python) чи TypeScript-компілятора:
  статичний аналіз, що знаходить помилки типів **до** запуску коду,
  аналізуючи PHP-типи (тема 07), яких у самій мові менше, ніж у
  TypeScript, але вже достатньо для потужного аналізу.
- `php-cs-fixer`/PHP_CodeSniffer — аналоги Prettier/`black`: автоматичне
  форматування коду під конкретний стандарт (типово PSR-12), а не
  просто підказки.

## 2. Ключові терміни

- **PSR-1 (Basic Coding Standard)** — базові правила: `StudlyCaps` для
  класів, `camelCase` для методів, `UPPER_SNAKE_CASE` для констант,
  файл або оголошує символи (класи/функції), або має side effects, не
  обидва одразу.
- **PSR-12 (Extended Coding Style)** — деталі форматування: відступи
  (4 пробіли, не таби), відкривна фігурна дужка класу/методу на новому
  рядку, один statement на рядок, і т.д.
- **Static analysis (статичний аналіз)** — пошук помилок **без**
  запуску коду, аналізом самого тексту/AST (PHPStan, Psalm) — на
  відміну від тестів (динамічний аналіз, потребує запуску).
- **Linter (лінтер)** — інструмент, що перевіряє стиль/типові помилки
  коду за правилами (не обов'язково виправляє сам).

## 3. Теорія

### 3.1 PSR-1: іменування

```php
class InvoiceGenerator     // StudlyCaps — класи
{
    public const MAX_ITEMS = 100;  // UPPER_SNAKE_CASE — константи

    public function generateReport(): string   // camelCase — методи
    {
        // ...
    }
}
```

### 3.2 PSR-12: форматування

```php
// НЕ так (стиль "Allman" для класів, брекет на тому самому рядку для методів PHP не використовує):
class Foo {
	public function bar() {
		return 1;
	}
}

// А ТАК (PSR-12: фігурна дужка класу/методу — на новому рядку, 4 пробіли, не таб):
class Foo
{
    public function bar()
    {
        return 1;
    }
}
```

### 3.3 PSR-4: іменування шляхів (нагадування з теми 38)

PSR-4 — теж стандарт PHP-FIG, розглянутий окремо в темі 38: простір
імен класу відповідає шляху до файлу.

### 3.4 Інструменти: PHPStan і `php-cs-fixer`

```bash
composer require --dev phpstan/phpstan
vendor/bin/phpstan analyse src/

composer require --dev friendsofphp/php-cs-fixer
vendor/bin/php-cs-fixer fix src/ --rules=@PSR12
```

```php
function add(int $a, int $b): int
{
    return $a . $b; // PHPStan: попередить, що конкатенація рядків для типів int — підозріла
}
```

PHPStan аналізує типи (параметри/повернення з теми 07, властивості
класів) і знаходить неузгодженості статично — до того, як цей код хоч
раз виконається. `php-cs-fixer` натомість не шукає логічних помилок —
він **автоматично переформатовує** код під обраний стандарт (PSR-12).

## 4. Підводні камені

- PSR-1/12 — про **форму** коду (іменування, відступи, розташування
  дужок), не про його **правильність**. Код може бути ідеально
  відформатованим і при цьому містити логічний баг — форматери й
  лінтери доповнюють тести (тема 44), не замінюють їх.
- Змішування табів і пробілів для відступів — джерело "діффів, де
  нічого не змінилось, але git показує зміни в кожному рядку" —
  PSR-12 явно вимагає 4 пробіли, не таби, саме для уникнення цього.
- `php-cs-fixer`/PHPStan — це `composer require --dev` (`--dev` — лише
  для розробки, не потрапляє в продакшн-залежності `require`) —
  плутанина `require` й `require --dev` — джерело зайвих пакетів у
  продакшн-збірці.

## 5. Сучасний PHP 8.3+

PHPStan/Psalm стають **точнішими** з кожною новою версією PHP, що додає
більше синтаксису для вираження типів (readonly з 8.1, intersection
types з 8.1, `never`-тип з 8.1) — статичний аналіз у сучасному PHP
ловить дедалі більше класів помилок, які раніше проявлялись лише в
рантаймі.

## 6. Контекст екосистеми

Практично кожен серйозний PHP-проєкт на GitHub має в CI (тема 48) кроки
`vendor/bin/phpstan analyse` і `vendor/bin/php-cs-fixer fix --dry-run`
поруч із тестами — "зелений" PR означає і "проходять тести", і
"відповідає стандартам стилю", перевірені автоматично, а не в
код-рев'ю вручну.
