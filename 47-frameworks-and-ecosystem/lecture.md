# 47. Фреймворки та екосистема

> Що ти вже вмієш: Express vs NestJS vs Next.js (JS), Flask vs Django
> (Python) — той самий вибір "мінімалізм чи все-в-комплекті" · Що додає
> ця тема: конкретна карта PHP-екосистеми — коли голий PHP, коли
> мікрофреймворк, коли повний фреймворк, коли WordPress · ~20 хв

## 1. Якщо ти прийшов з JS / Python / Java

- Laravel — приблизно те, що Django для Python чи Rails для Ruby:
  "batteries included", своя ORM, шаблонізатор, аутентифікація,
  черги — все з коробки, узгоджене між собою.
- Symfony — ближче до Spring (Java): менш "з коробки", більше
  окремих, незалежних компонентів, які можна брати частково (сам
  Symfony `HttpFoundation`/`Routing` використовують і Laravel, і
  Drupal під капотом).
- Slim — аналог Express (Node) чи Flask (Python): мінімалістичний
  роутер + мідлвари, без нав'язаної структури проєкту.
- WordPress — не зовсім "фреймворк" у звичному сенсі: це CMS
  (Content Management System) з готовою адмінкою й системою плагінів
  — ближче до того, що дає WIX/Webflow разом з можливістю писати
  код, ніж до Laravel/Django.

## 2. Ключові терміни

- **Мікрофреймворк** — мінімальний каркас (роутинг + базові
  абстракції запиту/відповіді), без нав'язаної структури проєкту чи
  вбудованої ORM (Slim, Lumen).
- **Full-stack фреймворк** — повний комплект: ORM, шаблонізатор,
  аутентифікація, черги, консольні команди, узгоджені між собою
  (Laravel, Symfony з FrameworkBundle).
- **CMS (Content Management System)** — система керування контентом із
  готовою адмінкою для непрограмістів (WordPress, Drupal) — код пишеться
  поверх готової системи, а не замість неї.
- **Convention over configuration (угода понад конфігурацію)** —
  філософія: якщо дотримуватись угоджених імен/структури (Laravel:
  `app/Models/User.php` — модель `User`), не треба явно конфігурувати
  кожен зв'язок вручну.

## 3. Теорія

### 3.1 Коли голий PHP (без фреймворка)

- Дуже маленький проєкт (кілька сторінок, один API-ендпоінт).
- Навчальні цілі — зрозуміти, що саме роблять фреймворки "під капотом"
  (саме це й був сенс тем 28-46 цього курсу).
- Максимальний контроль над продуктивністю, нуль зайвих залежностей.

### 3.2 Коли мікрофреймворк (Slim та подібні)

- Невеликий REST API, де не потрібна повна ORM чи шаблонізатор.
- Команда хоче сама вирішувати структуру проєкту, а не приймати
  нав'язану фреймворком.

### 3.3 Коли full-stack фреймворк (Laravel/Symfony)

- Проєкт середнього-великого розміру з БД, автентифікацією, формами —
  типовий "бізнес-застосунок".
- Laravel: швидший старт, більше "магії" (Eloquent ORM,
  facade-патерн), величезна спільнота й пакети.
- Symfony: більш явний, менше "магії", кращий вибір, коли потрібен
  повний контроль над кожним компонентом чи інтеграція в існуючу
  складну систему (Symfony-компоненти використовує сам Laravel і
  багато інших проєктів).

### 3.4 Коли WordPress

- Контентний сайт (блог, корпоративна сторінка, невеликий магазин),
  де замовнику потрібна адмінка для **нетехнічних** людей.
- Швидкий старт через готові теми/плагіни — ціна: менший контроль над
  архітектурою, історично слабша типізація в самому ядрі WordPress
  (значна частина коду ядра — доPHP-8 стиль).
- **Не** типовий вибір для складної бізнес-логіки чи API — WordPress
  оптимізований під "контент + адмінка", не під довільні застосунки.

## 4. Підводні камені

- "Фреймворк зробить код кращим сам по собі" — ні: фреймворк дає
  структуру й готові рішення для типових задач, але архітектурні
  помилки (змішування шарів, відсутність тестів) однаково можливі
  всередині Laravel-проєкту, як і в голому PHP.
- Вибір WordPress для проєкту зі складною кастомною бізнес-логікою —
  часта помилка: WordPress **можна** змусити робити що завгодно
  (є REST API, можна писати плагіни), але це часто важче, ніж почати
  з Laravel/Symfony напряму, якщо кінцева мета — не контентний сайт.
- Переоцінка "магії" full-stack фреймворка без розуміння, що саме
  відбувається "під капотом" — саме тому цей курс спершу пройшов
  голий PHP (блоки D-F) і лише тепер згадує фреймворки: розуміння
  `front controller`/DI/PDO робить документацію Laravel/Symfony
  зрозумілою, а не "чорною магією".

## 5. Сучасний PHP 8.3+

Усі великі фреймворки (Laravel 11+, Symfony 7+) вимагають PHP 8.2+ і
активно використовують сучасні можливості мови з цього курсу:
`readonly`-властивості (тема 13) для DTO, enum-и (тема 18) для
представлення станів, атрибути (`#[Route(...)]` у Symfony) замість
старих докблок-анотацій.

## 6. Контекст екосистеми

Packagist (реєстр Composer-пакетів, тема 38) — спільна база для всієї
екосистеми: і Laravel-пакети, і Symfony-компоненти, і незалежні
бібліотеки (Monolog, Guzzle) встановлюються тим самим `composer
require`. Це і робить можливим використання Symfony-компонентів
усередині Laravel-проєкту чи навпаки — усі говорять одним "мовою"
Composer + PSR-стандартів (тема 39).

## 8. Питання для самоперевірки

1. Чим мікрофреймворк принципово відрізняється від full-stack
   фреймворка — не за розміром, а за філософією?
2. Чому WordPress не завжди правильний вибір, навіть якщо він "уміє"
   зробити що завгодно через плагіни?
3. Що означає "convention over configuration" на прикладі Laravel?
4. Чому розуміння голого PHP (блоки D-F) полегшує роботу з
   фреймворком, а не є "зайвим" знанням для тих, хто однаково буде
   писати на Laravel?
